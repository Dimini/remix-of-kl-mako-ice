

# Fix voting import: regenerate types + unblock pdf-parse build

## What's actually happening

Claude Code's three CAP-03 migrations **are already applied** to your Supabase project — I confirmed `jurisdictions` exists with the seed row, `votes.jurisdiction_id` column is present, and the RLS policies are live. So nothing needs re-applying on the database side.

The two visible errors come from a different problem:

1. **TypeScript build errors in `AdminVotingImport.tsx`** (lines 88, 90, 95 — `'jurisdictions' is not assignable to parameter of type 'never'`) — this means `src/integrations/supabase/types.ts` is **out of sync** with the live database. That file is auto-regenerated by Lovable only when migrations go through the Lovable migration pipeline. Claude Code pushed directly via `supabase db push`, so Lovable never refreshed the types file.

2. **`pdf-parse` resolution error** in the edge functions typecheck — `supabase/functions/deno.json` has `"nodeModulesDir": "auto"` but the typechecker still bails. The dynamic `await import("npm:pdf-parse@1.1.1")` is the trigger, used in both `analyze-program` and `parse-voting-record`.

## Plan

### Step 1 — Regenerate `src/integrations/supabase/types.ts`

Run a no-op schema migration through the Lovable migration tool (e.g. `COMMENT ON TABLE public.jurisdictions IS '…';`). Lovable detects the schema activity and regenerates `types.ts` from the live database, picking up `jurisdictions`, `votes.jurisdiction_id`, and any other Claude-Code-applied changes.

This single step fixes the three `AdminVotingImport.tsx` TS errors with no code changes.

### Step 2 — Unblock the `pdf-parse` import

Two changes to make the typechecker stop failing on `npm:pdf-parse@1.1.1`:

- Add an explicit `imports` entry to `supabase/functions/deno.json`:
  ```json
  {
    "nodeModulesDir": "auto",
    "imports": { "pdf-parse": "npm:pdf-parse@1.1.1" }
  }
  ```
- Change the dynamic imports in `analyze-program/index.ts` and `parse-voting-record/index.ts` from `await import("npm:pdf-parse@1.1.1")` to `await import("pdf-parse")`. Keeps lazy loading (only fetched when a PDF actually arrives) but lets the typechecker resolve the spec via the import map.

### Step 3 — Verify

After deploy:
1. `/admin/voting-import` loads without TS errors, jurisdictions dropdown populates with the KVP seed row.
2. Run a dry-run import with the KVP PDFs to confirm the edge function executes end-to-end.

If step 2 still fails on `pdf-parse` after the import-map change, the fallback is to vendor `pdf-parse` via a Deno-native esm.sh URL (`https://esm.sh/pdf-parse@1.1.1?target=deno`) — same lazy-import shape, no npm resolution needed.
